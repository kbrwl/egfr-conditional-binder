# `design/configs/diagnostic/` — test configurations, not campaign files

Everything in `design/configs/` proper is generated by `analysis/09_trim_target.py`
and must not be hand-edited. The files in this subfolder are different: they are
written by hand to answer one question with one cheap run, and they are kept apart
so that nothing here is ever mistaken for the campaign.

Nothing in this folder defines what we submit. If a diagnostic here produces a
result that should change the campaign, the change belongs in `analysis/09` behind
its own constant, and the decision belongs to the owner — not to a file in this
folder.

---

## `ext499-notag.json`

**Question it answers:** does the extended target fragment clear BindCraft2's
target-confidence gate on its own, with no filter relaxed?

**Why it was written (2 October 2026).** The validation run against the committed
fragment was stopped at its first stage. The cause was `pLDDT.EGFR_domain3 = 0.35`
against BindCraft2's default floor of `Target_pLDDT >= 0.6` — the predictor's
confidence in **our target**, not in the binder it was designing. Because that
figure barely moves with the binder (the PD-L1 smoke run's varied by 0.01 across ten
designs), the same gate would be expected to stop essentially every attempt, so a
full campaign against this fragment would spend the budget and accept nothing.

Two explanations fit, and they call for different fixes:

1. **The fragment does not hold its shape.** The cut severs one disulfide bond,
   between C470 inside the fragment and C499 outside it. This has been the standing
   Unverified item in `docs/decisions-log.md` since the cut was made.
2. **The predictor is the problem, not the fragment.** BindCraft2 runs AlphaFold
   with no evolutionary information (`extra_msa` is zeroed in `bindcraft/af2.py`),
   which is much harder for a large beta-solenoid than for PD-L1's compact and
   well-known fold. ESMFold rates this same fragment 80.6 — above the usual
   reliable-backbone convention of about 70. And the default the filter uses is
   named `DEFAULT_DISORDERED_TARGET_PLDDT`, which suggests a floor meant for targets
   supplied as a bare sequence rather than, as ours is, as a structure whose
   coordinates are supplied and held.

This file tests the first explanation, by extending the cut to 310–499 so the
severed disulfide has its partner back. If target confidence rises above 0.6 on its
own, the fragment was the problem and no rejection rule needs touching. If it stays
near 0.35, the fragment is not the problem and the filter is.

**What differs from the committed campaign:** the target file, and nothing else.
The hotspots are unchanged and are still correct, because the extended fragment
keeps 6ARU's own numbering exactly as the committed one does. Binder lengths,
the His-tag off-target, its weight, and `termini_accessible` are all identical, so
the comparison isolates the boundary.

**The fragment it points at.** `data/structures/6aru_domain3_ext499.pdb`, 190
residues against the committed fragment's 171, cut from the same receptor-only
structure by the same method. Over the residues the two fragments share, the atom
records are byte-identical, so the two differ only in where they stop. Both C470 and
C499 are present, so the disulfide can form.

**Regenerate it with `python design/configs/diagnostic/cut_ext499.py`.**
`data/structures/` is deliberately untracked, so the fragment itself is not
committed and the script is what carries the record. It copies its cutting method
from `analysis/09_trim_target.py` rather than reinventing one — same source file,
same selection by structure-file residue number, same writer — and it ends by
checking that its own output reproduces `6aru_domain3.pdb` exactly over the residues
the two share. That check is the point: if the two fragments were cut by different
methods, comparing their results would measure the method rather than the boundary.
The script was verified by deleting the fragment and rebuilding it, which reproduced
it identically.

**What this does not settle.** `results/findings/11-trim-boundary.md` already
compared these two boundaries with ESMFold and found no difference on the anchor
face — the eight positions the design run actually aims at fitted at 0.64 against
0.65 angstroms. What the extension improved there was the cut edge, from 54.4 to
78.2 confidence, which is a region only one anchor is near. So a pass here would
mean the extension helps BindCraft2's predictor specifically, and would not
retrospectively make step 11's measurement wrong. The recorded decision that the
boundary stays 310–480 still stands until the owner moves it.
